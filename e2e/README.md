# Lowcoder end-to-end tests (Playwright)

Playwright suite (Chromium only) for the Lowcoder all-in-one Docker image. It checks that the web client and the
bundled backend work together: sign-up and sign-in, app lists, the editor (insert, move, resize, rename, properties,
queries), the published view, PostgreSQL queries and tables, query triggers, temporary state, local storage, modules,
the Extensions panel and the visual components. Apps are seeded through the HTTP API from DSL built by helpers
(`src/dsl/builders.ts`) and opened in the published view; the editor is driven only where the editor is the subject.

Rules for writing or changing tests: [AGENTS.md](AGENTS.md).

Not covered: Firefox and WebKit; the multi-container compose setup; databases other than PostgreSQL (the data sources that run in node-service are covered by their catalogue, D3: which plugins the image serves and that each definition has a form and a query config; of the plugins DuckDB runs queries, D4, embedded in the app container with no network, and Turso, Slack, GitLab, Shopify, the generic Open API plugin and the Open API wrappers CouchDB, Jira, Datadog, WooCommerce, Supabase Management API, Lowcoder API, OpenAI, APITemplate.io and Carbone run queries (and, for Open API, build the data source form's dynamic config from a document the echo serves), and DynamoDB and S3 (AWS SDK v3, signed requests; the S3 calls that take a bucket go to the echo's IP address, `E2E_ECHO_IP`, never to the alias), D5 to D10, and Supabase Storage (supabase-js against a project URL on the echo, the key in `apikey` and `authorization`), D11, against the echo sidecar, which proves the request they build and the path of a canned answer into the app, not the vendor service; Firebird (node-firebird over TCP, D12) runs against a Firebird sidecar of its own that only a run with `E2E_INCLUDE_NODE_SERVICE_SIDECARS=1` starts, and a default run neither starts it nor lists or runs those tests, and Turso also runs against a real libSQL server (sqld, D13) the same way, where the `libsql://` to `https://` rewrite of the URL is not covered because the sidecar speaks plain HTTP, and CouchDB also runs against a real Apache CouchDB server (D14) the same way, where the JWT credential and cookie sessions are not covered because the image's default configuration has no JWT authentication handler and the plugin sends the `Authorization` header only, and DynamoDB also runs against a real DynamoDB Local server (D15) the same way, where indexes, transactions, batch operations, streams and the request signature (the server verifies none) are not covered, and S3 also runs against a real S3-compatible server (versitygw, D16) the same way, reached by its IP address only (it has no name), where a real AWS S3, multipart upload, an expired presigned URL, versioning and ACLs are not covered; the UiPath plugin fails every query and its query configuration before it sends a request (D9, D-71 candidate); no other plugin query is run yet); the server and
node-service as separate units; any request to a real external host (the network guard blocks them); the app-level
layouts `navLayout` and `mobileTabLayout` (open decision). The functional behaviour of the nine components that need a
cloud service, credentials, third-party scripts or a device (3 Agora meetings, `turnstileCaptcha`, `scanner`,
`chartsGeoMap`, `openLayersGeoMap`, `hillchart`, `jsonLottie`, the components of the "cloud service or device" class) is not covered; their structural
lifecycle (insert, save, publish, load) is covered by S1 when `@insert-all` runs. No CI workflow runs this suite
(`.github/workflows/` has no e2e job).

`e2e/evidence/` is git-ignored, local only, and is never a source for claims in git.

## Architecture

- **Image under test:** `lowcoderorg/lowcoder-ce:3.0.0-e2e` = the published `3.0.0` all-in-one image with its web client
  rebuilt from tag `3.0.0` plus [client-hooks.patch](client-hooks.patch). The patch adds test hooks (`data-editor-ready`,
  `data-testid="insert-comp-<type>"` on insert-panel tiles, `role="tab"`/`role="tablist"`, `data-comp-name`), but it also
  touches the editor's save code (`appEditorInternal.tsx`). A defect found on this image is assumed to exist in 3.0.0
  only where the patch does not touch the involved code; that equivalence is NOT VERIFIED. The image is a locally built tag.
  The latest assessed image is `lowcoderorg/lowcoder-ce:3.0.1-e2e` (run of 2026-11-22; the plain `3.0.0-e2e` rows below were measured on the
  earlier image). `client-hooks.patch` no longer applies to `dev`: the test hooks are committed there (from the repository root,
  `git apply --check e2e/client-hooks.patch` fails and `git apply --check -R e2e/client-hooks.patch` succeeds, checked 2026-11-22), so the patch is
  needed only to rebuild an image from the `3.0.0` tag.
- **Isolated Docker network per run:** `scripts/run-in-docker.sh` creates `lowcoder-e2e-<pid>-net`, starts the app
  container and a PostgreSQL sidecar, waits for `GET /api/configs`, runs Playwright from
  `mcr.microsoft.com/playwright:v1.64.0-noble` with `e2e/` bound at `/work`, and removes everything on exit. Every run
  executes `npm ci` inside the runner, so the runner needs access to the npm registry (and Docker must be able to pull
  the images) even when `@npm` tests are excluded. There is no offline mode.
- **PostgreSQL sidecar:** `postgres:17-alpine` (pinned by digest) with `fixtures/sql/init.sql`: `items` (2 rows),
  `products` (25 shared read-only rows), `notes` (writes, owner-scoped). Host name in `E2E_POSTGRES_HOST`; connection
  constants are `POSTGRES` in `src/constants.ts`. The image declares `/var/lib/postgresql/data` a volume (`docker inspect` shows `{"/var/lib/postgresql/data":{}}`), so the script mounts a tmpfs there: the database is in memory (it is thrown away with the run anyway; the init scripts come from the read-only mount at `/docker-entrypoint-initdb.d`, not from that path) and no anonymous volume outlives the run.
- **Firebird sidecar (opt-in):** the Firebird plugin of node-service speaks the Firebird wire protocol over TCP, which the HTTP echo cannot stand in for, so its tests (D12, `tests/datasource/plugin-firebird.spec.ts`) run against a real Firebird server. It is OPT-IN:
  - **Flag and tag:** `E2E_INCLUDE_NODE_SERVICE_SIDECARS=1` (`RUN_FLAGS.INCLUDE_NODE_SERVICE_SIDECARS`) and the tag `@node-service-sidecar` (`TAGS.NODE_SERVICE_SIDECAR`), worn next to `@node-service`. The default selection leaves the tag out (`excludedTags` in `src/run-selection.ts`), exactly like `@superadmin`.
  - **A default run** (no flag) starts no Firebird container, pulls no Firebird image, passes no `E2E_FIREBIRD_HOST` to the runner, and neither lists nor runs the D12 tests (`--list` shows 0 for `--grep @node-service-sidecar`). **A run with the flag** starts the sidecar after the echo, waits until a SELECT of the seeded table through the image's own `isql` answers over TCP, gives the app container and the runner the entry `--add-host e2e-firebird:<IP>` (the same reason as the echo's: the name must not fall back to an outside resolver), passes `E2E_FIREBIRD_HOST=e2e-firebird` to the runner, and removes the container in the cleanup trap however the run ends. The flag is refused on another stack profile (those runs select no sidecar test). A test selected without the sidecar fails with a named error (`firebirdConnection()` throws when the host variable is unset).
  - **Image:** `firebirdsql/firebird:3.0.12`, pinned by tag and digest (`sha256:e45c9bc4fdacaaddc1980a05b7bb8b297f09fe019eadefb059006efe4dafe875`; `FIREBIRD_IMAGE` overrides it), data from `fixtures/firebird/init.sql` (`FB_ITEMS`, 3 read-only rows; `FB_NOTES`, writes scoped by owner), throw-away user and password in `FIREBIRD` of `src/constants.ts` and in the script. The image declares `/var/lib/firebird/data` a volume, so the script mounts a tmpfs there (the database file `e2e.fdb` lives in it, stays writable and is in memory: the D12 insert and error scenarios pass, 110 of 110 in the gate) and no anonymous volume outlives the run. Why this one, measured with node-firebird 1.1.9 (the version node-service installs) from the runner: 3.0.12, 4.0.5 and 5.0.4 all refuse the attach with the image's defaults (3.0.12 and 5.0.4: "Incompatible wire encryption levels requested on client and server", WireCrypt `Required`; 4.0.5: "Error occurred during login"). 4.0.5 and 5.0.4 attached with `FIREBIRD_CONF_AuthServer=Srp,Legacy_Auth` plus `FIREBIRD_CONF_WireCrypt=Disabled` (one attempt each). 3.0.12 attached with `FIREBIRD_CONF_WireCrypt=Enabled` or `FIREBIRD_USE_LEGACY_AUTH=true`, but with its default Srp login 12 of 100 attaches failed with "Your user name and password are not defined" (node-firebird's client-side Srp; also seen through the app: 4 of 14 queries of one probe), while with `FIREBIRD_USE_LEGACY_AUTH=true` 100 of 100 attached. The sidecar therefore runs 3.0.12 with `FIREBIRD_USE_LEGACY_AUTH=true` (Legacy_Auth first, WireCrypt `Enabled`). Limit of that choice: Legacy_Auth compares only the first eight characters of a password (measured: a wrong password that shares them attached), so the wrong password of D12b differs within them; the sidecar is not evidence about the Srp login of Firebird 3, 4 or 5, which node-firebird 1.1.9 fails at random.
  - **Run only these:** `E2E_INCLUDE_NODE_SERVICE_SIDECARS=1 e2e/scripts/run-in-docker.sh --grep @node-service-sidecar` (or name the spec file).
  - **Cost, measured here:** image 156 MB (`docker image inspect`), a cold pull of the pinned digest took 3 s (a fast link and a warm registry mirror: expect more elsewhere), the container accepted the readiness SELECT within about 3 s of starting (the script logged `Firebird sidecar ready after 0s`: the wait ran after the PostgreSQL wait of 2 s), and a gate of 110 tests ran in about 23 s. Runs without the flag pay nothing.
- **libSQL sidecar (opt-in):** the Turso plugin of node-service posts Hrana pipelines to `<url>/v2/pipeline` over HTTP, so the echo can stand in for it (D5, canned answers); a real server adds what canned answers cannot: the real column types and cells, real SQL errors, real authentication (D13, `tests/datasource/plugin-turso-libsql.spec.ts`). It is OPT-IN under the same flag and tag as the Firebird sidecar and the sidecars start together:
  - **A default run** starts no libSQL container, pulls no libSQL image, passes no `E2E_LIBSQL_HOST` to the runner, and neither lists nor runs the D13 tests. **A run with the flag** starts the sidecar right after the Firebird one, waits (`STARTUP_TIMEOUT`, 300 s of real elapsed time, polled every 2 s; see "Readiness bound" under the DynamoDB Local sidecar) until one real `select 1` pipeline with the read-write token, posted from the echo container to `http://e2e-libsql:8080/v2/pipeline` over the run network, answers 200 with the integer 1, gives the app container and the runner `--add-host e2e-libsql:<IP>` (added to the Firebird entry, not replacing it), passes `E2E_LIBSQL_HOST=e2e-libsql` to the runner, and removes the container in the cleanup trap however the run ends. The data source URL is `http://e2e-libsql:8080` (`libsqlConnection()` throws a named error when the host variable is unset).
  - **Image:** `ghcr.io/tursodatabase/libsql-server:v0.24.33`, sqld 0.24.33, pinned by tag and digest (`sha256:f8ca0134cdded747793888e48591aece07647d9d598d3ac229aabfa93159ca88`; `LIBSQL_IMAGE` overrides it). It is the libSQL project's own server image. Its `latest` tag, pulled at the same time, was another build that also reports sqld 0.24.33 (digest `sha256:6dd3eb276d9d3604e4a48ac4a999a2e267814732d57d7e94c04ba71482333a67`), so the pin uses the version tag. The image declares `/var/lib/sqld` a volume, so the script mounts a tmpfs there: the database is in memory and no anonymous volume outlives the run.
  - **Auth setup:** sqld started with `SQLD_AUTH_JWT_KEY` accepts only a JWT signed with the matching Ed25519 key (a plain `--http-auth` would want Basic credentials, but the plugin sends `Authorization: Bearer <token>`). A key pair was generated once and its private half thrown away; `LIBSQL` in `src/constants.ts` and `LIBSQL_JWT_PUBLIC_KEY` / `LIBSQL_TOKEN` in the script hold the public key and tokens signed with it, without an expiry: a read-write token (claim `a: "rw"`), a read-only one (`a: "ro"`, the server answers 403 to a write) and a "foreign" one signed by a second throw-away pair (the server answers 401). A foundation test verifies the three signatures against the public key. Without a token, with a malformed one or with the foreign one the server answers 401.
  - **Run only these:** `E2E_INCLUDE_NODE_SERVICE_SIDECARS=1 e2e/scripts/run-in-docker.sh tests/datasource/plugin-turso-libsql.spec.ts` (every sidecar starts; `--grep @node-service-sidecar` runs D12 and D14 as well).
  - **Cost, measured here:** the image is 153 MB (`docker image inspect`, uncompressed) and a cold pull of the pinned digest took 9 s (a fast link: expect more elsewhere); the container started with the Firebird one and answered the readiness call within about a second (the script logged `libSQL sidecar ready after 0s`, the wait running after the PostgreSQL, echo and Firebird waits), so the two sidecars together add no waiting of their own beyond the slower one; a gate of 110 tests (`--repeat-each=10 --workers=4`) ran in about 27 s. Runs without the flag pay nothing. The readiness bound is described under the DynamoDB Local sidecar.
- **CouchDB sidecar (opt-in):** the CouchDB plugin of node-service is an OpenAPI wrapper that sends HTTP, so the echo can stand in for it (D8a to D8i, canned answers); a real server adds what canned answers cannot: the server's own status codes and error bodies, stored documents and revisions, key ranges, real authentication and its lockout (D14, `tests/datasource/plugin-couchdb.spec.ts`). It is OPT-IN under the same flag and tag as the other sidecars and all three start together:
  - **A default run** starts no CouchDB container, pulls no CouchDB image, passes no `E2E_COUCHDB_HOST` to the runner, and neither lists nor runs the D14 tests (`--list --grep @node-service-sidecar` shows 0). Measured: the containers a default run created (`docker events`) were the app, the echo, PostgreSQL and the runner. **A run with the flag** starts the sidecar right after the libSQL one, waits (`STARTUP_TIMEOUT`, 300 s of real elapsed time, polled every 2 s; the whole probe of five requests has one 5 s budget and each request a 2 s connect limit; see "Readiness bound" under the DynamoDB Local sidecar) until the server answers `_up`, creates the system databases (a `PUT` counts only on 201 or 412) and lists them, gives the app container and the runner `--add-host e2e-couchdb:<IP>` (appended to the entries of the other sidecars), passes `E2E_COUCHDB_HOST=e2e-couchdb` to the runner, and removes the container in the cleanup trap however the run ends. The data source URL is `http://e2e-couchdb:5984` (`couchdbConnection()` throws a named error when the host variable is unset). Reached from both sides: the plugin's requests come from the app container, and D14i and the direct calls come from the runner.
  - **Image:** `couchdb:3.5.1`, Apache CouchDB 3.5.1 (the official image; the plugin bundles the 3.1.1 API document), pinned by tag and digest (`sha256:ccea1e8035bf7afd68336e24056a1ca9c1c46d7abe42da686322c0ac7218e5c2`; `COUCHDB_IMAGE` overrides it). The image declares `/opt/couchdb/data` a volume, so the script mounts a tmpfs there: the data is in memory and this sidecar leaves no anonymous volume (measured: `docker inspect` of the running container shows `Mounts` empty and the tmpfs; see the dangling-volumes evidence in the counts paragraph below).
  - **Admin setup:** the image makes one server admin from `COUCHDB_USER` and `COUCHDB_PASSWORD` (`COUCHDB` in `src/constants.ts` and the script: `e2eadmin` and a throw-away password, never a real secret). A fresh single node has no system databases (`_all_dbs` answers `[]`), so the readiness step creates `_users`, `_replicator` and `_global_changes` with `PUT` through the real HTTP API (201, or 412 when they exist) and is ready when `_all_dbs` lists all three; it runs inside the container (the image has curl), is idempotent, and is repeated until it succeeds. The tests make their own databases (`e2e_couch_<hex>`) and remove them.
  - **Lockout (measured, CouchDB 3.5.1):** after five failed logins of a real account the server answers 403 `Account is temporarily locked due to multiple authentication failures` to that account, from that client address, even with the right password (the message says "temporarily"; how long it lasts was not measured). A test that sends a wrong password therefore does it as a second admin it makes for the purpose (D14e, D14j) and never as the sidecar's admin, which every other test uses; failures for a name that does not exist are not counted. A freshly made config admin cannot log in until the server has hashed its password (a moment after the `PUT`), so the helper waits for the hash before the first login.
  - **Run only these:** `E2E_INCLUDE_NODE_SERVICE_SIDECARS=1 e2e/scripts/run-in-docker.sh tests/datasource/plugin-couchdb.spec.ts` (every sidecar starts under the flag, five today; `--grep @node-service-sidecar` runs the other sidecar tests as well).
  - **Cost, measured here:** the image is 276 MB (`docker image inspect`, uncompressed); CouchDB answered the readiness probe on its first try, about a second after it started (the script logged `CouchDB sidecar ready after 0s`: the wait runs after the PostgreSQL, echo, Firebird and libSQL waits, and the server's log shows it started in about half a second), so all three sidecars together added no waiting of their own beyond the slowest. A cold pull of the pinned digest took 6.4 s (a fast link: expect more elsewhere). The readiness bound is described under the DynamoDB Local sidecar. A test that fails still ends with every container and the network removed (measured with a deliberately failing test under the flag: seven containers created, none left, no network left).
- **DynamoDB Local sidecar (opt-in):** the DynamoDB plugin of node-service uses the AWS SDK v3 with a configurable endpoint, so the echo can stand in for it (D10a to D10f, canned answers and the signed request); a real server adds what canned answers cannot: real tables and items, the typed attribute form on the wire, pagination keys, and the server's own errors (D15, `tests/datasource/plugin-dynamodb-local.spec.ts`). It is OPT-IN under the same flag and tag as the other sidecars and all four start together:
  - **A default run** starts no DynamoDB Local container, pulls no DynamoDB Local image, passes no `E2E_DYNAMODB_HOST` to the runner, and neither lists nor runs the D15 tests (`--list --grep @node-service-sidecar` shows 0). **A run with the flag** starts the sidecar right after the CouchDB one, waits (`STARTUP_TIMEOUT`, 300 s of real elapsed time, polled every 2 s; every readiness request is aborted after 5 s; see "Readiness bound" below) until one real `ListTables` call, posted from the echo container to `http://e2e-dynamodb:8000/` over the run network, answers exactly 200 with a JSON body whose `TableNames` member is an array, gives the app container and the runner `--add-host e2e-dynamodb:<IP>` (appended to the entries of the other sidecars), passes `E2E_DYNAMODB_HOST=e2e-dynamodb` to the runner, and removes the container in the cleanup trap however the run ends. The data source's endpoint is `http://e2e-dynamodb:8000` (`dynamodbConnection()` throws a named error when the host variable is unset). Reached from both sides: the plugin's requests come from the app container, and the direct calls and D15l come from the runner.
  - **Image:** `amazon/dynamodb-local:3.3.2` (AWS's own image, DynamoDB Local 3.3.2, Java 17), pinned by tag and digest (`sha256:6ada631ec7aa5fc83446855eb17233e3dad184fec47477e8140c6c569cfe0c86`, the digest of `3.3.2` and `latest` on Docker Hub when it was pulled; `DYNAMODB_IMAGE` overrides it). It runs `-jar DynamoDBLocal.jar -inMemory -sharedDb -port 8000`: every table is in memory (nothing is written to a file) and one database serves every access key, so table names are global to the sidecar and each test names its tables with a per-test marker (`e2e_ddb_<hex>`) and removes them in a `finally`. The image declares no volume (`docker image inspect` shows no `Volumes`), so no `--tmpfs` is needed: measured, the running container's `Mounts` is empty.
  - **Credentials:** the server checks none: it wants an `Authorization` header with a `Credential=` scope and accepts any access key and any signature (measured: a signature of zeros is accepted; a request without the header is refused with `MissingAuthenticationToken`). `DYNAMODB` in `src/constants.ts` holds a throw-away key, secret and region, never a real secret; the direct calls of the tests send the same header form with a signature of zeros.
  - **Readiness bound (the Firebird, libSQL, CouchDB, DynamoDB Local and S3 waits):** each loop takes the shell's `SECONDS` at its start and, after every failed probe, compares the elapsed seconds with `STARTUP_TIMEOUT` before it sleeps and probes again, so the time a probe takes counts (an earlier version added up its sleeps only: with probes that take 5 s each it ran several times past the limit). The check comes before the sleep and the next probe, and one probe is bounded as a WHOLE: the Firebird probe is one `isql` run under `timeout -s KILL 5`, the libSQL, DynamoDB and S3 probes are one fetch aborted after 5 s, and the CouchDB probe, which makes five requests (`_up`, three `PUT`s, `_all_dbs`), shares one 5 s budget (`couchdb_curl` gives each request the time left of the probe's deadline as its `--max-time`, and a request that finds nothing left is not made). So for each of the five the worst case is `STARTUP_TIMEOUT` + `POLL_INTERVAL` (2 s) + `PROBE_REQUEST_TIMEOUT` (5 s), that is 7 s past the limit, plus up to one second of clock granularity (`SECONDS` counts whole seconds) and the start-up time of the `docker exec` calls, which has no limit of its own; not an unbounded multiple. A foundation test fails for any of the five loops that goes back to the sleep-only counter (measured: with the S3 loop changed back to the sleep-only counter, together with five other changes to the script, five structural tests failed and the restored script passed them). The PostgreSQL, echo and app waits were not changed: they still add up their sleeps only and their probes have no time limit. Measured by hand on one machine, no artifacts committed, with temporary copies of the script (`STARTUP_TIMEOUT=6`): the sidecar's probe was made unable to succeed (DynamoDB: another accepted status; libSQL: a token the server refuses; CouchDB: other accepted statuses; Firebird: a table that does not exist) so that it failed fast, and 4 s after the container appeared the server was frozen (`docker pause` for DynamoDB and libSQL, whose probe runs in the echo container; SIGSTOP of the server processes for CouchDB and Firebird, whose probe runs inside the container), so that the probes were accepted by the kernel and never answered and each ended at its 5 s limit. Each run ended with `the <name> sidecar did not become ready within 6s` and no container or network left. Total duration of the script, start of the stack included (about 2 s): with the sleep-only counter 20 s for DynamoDB Local, 19 s for libSQL, 19 s for CouchDB and 19 s for Firebird; with the elapsed-time deadline 12 s for each of the four (the stack takes about 2 s, so the wait ended about 10 s after it began, inside the worst case of 6 + 2 + 5 = 13 s). CouchDB was measured again after its probe got the shared budget, three runs of the same method: 12 s, 13 s and 12 s. A frozen server stalls only the first request of its probe, so this method does not show the budget; the budget was shown with a stub `docker` that answers each of the five requests correctly but takes 3 s for it: the probe of the earlier form took 15 s and succeeded, the probe with the shared budget stopped after 5 s and failed, and a foundation test fails for the earlier form (the structural assertions of the probe's deadline). An earlier measurement of 10 s with a paused DynamoDB container did not exercise a stalled probe: the container was frozen before the server listened, so the connection was refused at once. The S3 loop was measured the same way (a temporary copy of the script with `STARTUP_TIMEOUT=6` and another accepted status, so that the probe could not succeed; the S3 container paused 4 s after it appeared, so the kernel accepted the connections and nothing answered): the script ended with `the S3 sidecar did not become ready within 6s` after 13 s in total (the stack takes about 2 s, so the wait ended inside the worst case of 6 + 2 + 5 = 13 s), and no container or network was left; the copy was deleted.
  - **Run only these:** `E2E_INCLUDE_NODE_SERVICE_SIDECARS=1 e2e/scripts/run-in-docker.sh tests/datasource/plugin-dynamodb-local.spec.ts` (every sidecar starts under the flag, five today; `--grep @node-service-sidecar` runs the other sidecar tests as well).
  - **Cost, measured here:** the image is 512 MB (`docker image inspect`, uncompressed); the JVM server answered the readiness call on its first try, within a second or two of starting (the script logged `DynamoDB Local sidecar ready after 0s`: the wait runs after the PostgreSQL, echo, Firebird, libSQL and CouchDB waits), so the sidecars were all ready about three seconds after the first container of the run was created, while the app needs 10 to 12 s (measured: `Application ready after 10s` and `after 12s` in flagged runs; the readiness waits run after the app container is started). A cold pull of the pinned digest took 10 s (a fast link: expect more elsewhere). A test that fails still ends with every container and the network removed (measured with twelve deliberately inverted assertions under the flag: none left, no network left). These results were measured by hand on one machine; no artifacts are committed. A gate of 120 tests (`--repeat-each=10 --workers=4`) ran in about 31 s. Runs without the flag pay nothing.
- **S3 sidecar (opt-in):** the S3 plugin of node-service uses the AWS SDK v3 with a configurable endpoint, so the echo can stand in for it (D10g to D10q, canned answers and the signed request); a real server adds what canned answers cannot: real buckets and objects, the bytes and content types that come back, listing behaviour, presigned URLs that can be fetched, the server's own errors and its verification of the signature (D16, `tests/datasource/plugin-s3-server.spec.ts`). It is OPT-IN under the same flag and tag as the other sidecars and all five start together:
  - **A default run** starts no S3 container, pulls no S3 image, passes no `E2E_S3_IP` to the runner, and neither lists nor runs the D16 tests (`--list --grep @node-service-sidecar` shows 0). **A run with the flag** starts the sidecar right after the DynamoDB Local one, waits (`STARTUP_TIMEOUT`, 300 s of real elapsed time, polled every 2 s; every readiness request is aborted after 5 s; see "Readiness bound" under the DynamoDB Local sidecar) until one real, SIGNED ListBuckets request, posted from the echo container to `http://<sidecar IP>:7070/` over the run network, answers exactly 200 with a `ListAllMyBucketsResult`, and removes the container in the cleanup trap however the run ends.
  - **Addressing (why this sidecar has an IP and no name):** the AWS SDK addresses a bucket of an endpoint that is a host NAME as `<bucket>.<host>` (virtual-host style), a name that no `--add-host` entry covers and that may resolve outside the run network; for an endpoint that is an IP address it uses path-style (`<endpoint>/<bucket>/<key>`) (measured in D10, and again against this server). So, unlike the other sidecars, this one has no network alias and no `--add-host` entry: the script reads the container's IP address on the run network when it starts it (`docker inspect`, like the echo's), passes it to the runner as `E2E_S3_IP` (`S3.IP_ENV` in `src/constants.ts`), and the data source's endpoint is `http://<that IP>:7070`. `s3Connection()` (`src/datasource/s3.ts`) reads it and throws a named error when it is unset (`S3SidecarMissingError`) or is not an IPv4 address (`S3SidecarAddressError`), like `echoUrlByIp` for `E2E_ECHO_IP`; the foundation tests check both and that the script names the variable once, adds no alias and no `--add-host`. Measured by hand (one machine, no artifacts committed): from inside the app container the sidecar answers by IP (an unsigned request: 403 `AccessDenied`, an S3 XML error), the name `e2e-s3` does not resolve there (`HTTP 000`), and a presigned URL made with the SDK for an object with a space in its key downloaded the object from the app container (HTTP 200, the content) and from the host. Reached from both sides in the tests: the plugin's requests come from the app container; the direct calls (`s3Direct`) and the presigned URLs of D16i come from the runner.
  - **Image:** `versity/versitygw:v1.11.0` (Versity S3 Gateway, Go, one static binary, started with its POSIX backend), pinned by tag and digest (`sha256:8319a530d08d537426e2f855bae5280709795dc73a3f0c347973ef915d6343c5`, the digest of `v1.11.0` and `latest` on Docker Hub when it was pulled; `S3_IMAGE` overrides it). It runs `--port :7070 --quiet posix --sidecar /meta /data` with two tmpfs mounts (`/data` the objects, `/meta` the metadata sidecar directory, so the server needs no extended attributes on the data directory): everything is in memory and nothing outlives the container. The image declares no volume (`docker image inspect` shows `Volumes: null`; measured: the running container's `Mounts` is empty and its `HostConfig.Tmpfs` is `/data` and `/meta`), so the two tmpfs mounts are directories the script chose, not volumes the image forced on it; the foundation test table of declared volumes lists them. The server is started in region `us-west-1` (`VGW_REGION`, the plugin form's default region); a bucket made in that region needs the location constraint in the create request (without it the server answers 400 `IllegalLocationConstraintException`, as AWS does), which the helper `s3CreateBucket` sends. Why this one, measured on this machine (2026-11-25): MinIO (`minio/minio` on Docker Hub: `denied: requested access to the resource is denied`; `quay.io/minio/minio:latest` and a 2025 release tag: `no such manifest`; `bitnami/minio:latest`: no such manifest) has no pullable community image. `adobe/s3mock:5.2.3` pulls (84 MB compressed, 134 MB on disk, a JVM; answered about 2 s after it started) but VERIFIES NOTHING: ListBuckets with a wrong access key and with a wrong secret both succeeded (measured with the AWS SDK), so no wrong-credential scenario could be written against it. `chrislusf/seaweedfs`, `zenko/cloudserver`, `dxflrs/garage` and `localstack/localstack` have manifests on Docker Hub but are multi-process or configuration-heavy servers (not run here). versitygw: 37 MB compressed (Docker Hub), 82 MB on disk, one process, in memory on tmpfs, path-style and virtual-host support, verifies AWS Signature Version 4 for every request.
  - **Auth setup:** one root user from the image's own variables `ROOT_ACCESS_KEY_ID` and `ROOT_SECRET_ACCESS_KEY` (`S3` in `src/constants.ts` and `S3_ACCESS_KEY`, `S3_SECRET_KEY` in the script: `e2eS3Key` and a throw-away secret, never real secrets; no key on the server's command line). The server VERIFIES the signature: measured with the SDK and again in D16a, D16b and D16k, a wrong access key is refused with 403 `InvalidAccessKeyId` ("The AWS Access Key Id you provided does not exist in our records."), a wrong secret with 403 `SignatureDoesNotMatch`, a request signed for another region with the authorization-header-malformed text naming the region it expects, and a request without a signature with 403 `AccessDenied`. So wrong-credential scenarios are real, unlike DynamoDB Local, which checks nothing.
  - **Run only these:** `E2E_INCLUDE_NODE_SERVICE_SIDECARS=1 e2e/scripts/run-in-docker.sh tests/datasource/plugin-s3-server.spec.ts` (all five sidecars start; `--grep @node-service-sidecar` runs D12 to D15 as well).
  - **Cost, measured here:** the image is 82 MB on disk (`docker image inspect`) and a cold pull of the pinned tag took 2.9 s (a fast link: expect more elsewhere); the sidecar answered the readiness request within a second of starting (the script logged `S3 sidecar ready after 0s` or `1s`: the wait runs after the PostgreSQL, echo, Firebird, libSQL, CouchDB and DynamoDB Local waits). With all five sidecars the script logged the first `Starting` line at 08:07:56 and the last sidecar ready at 08:07:58, and `Application ready after 10s` (12 s after the first container; the sidecar waits run after the app container is started, so they delay nothing). A gate of 150 tests (`--repeat-each=10 --workers=4`) ran in about 35 s. Runs without the flag pay nothing. The readiness bound is described under the DynamoDB Local sidecar. These results were measured by hand on one machine; no artifacts are committed.
- **HTTP echo sidecar** (`scripts/echo-server.js`, started by `run-in-docker.sh` on the already pinned runner image, so no extra image or
  download; network alias `e2e-echo`, port 8080; the runner gets `E2E_ECHO_URL` and the sidecar's IP address on the run network as `E2E_ECHO_IP`): the target of the requests the SERVER makes inside the
  app container (node-service's npm registry proxy, the n8n plugin). It records `{ method, path, headers, body }` of every request in
  memory (bodies cut at 65536 bytes, 10000 records kept) and answers `{}`; `GET /__e2e/requests?prefix=<p>` returns the records whose
  path starts with `<p>`. The `echo` fixture of `src/fixtures.ts` gives each test its own target `<E2E_ECHO_URL>/t/<worker>-<repeat>-<retry>-<random>`
  (`url`, `received()`), so parallel tests never read each other's records; its one request context is created on first use and
  disposed after the test. The records die with the container (`cleanup` removes it however the run ends). Limits: the browser guard
  does not apply to these requests (they are made by the backend), so the echo is the only host the tests point the backend at; the
  sidecar starts in every run, also on the enterprise profile; an echo test that finds nothing proves nothing unless a positive control
  shows that the echo does receive from that path (every denial row of `outbound*.spec.ts` has one). The app and runner containers resolve `e2e-echo` through `--add-host e2e-echo:<sidecar IP>` (read with `docker inspect` after the sidecar starts), not DNS: measured with the sidecar stopped, `getent hosts e2e-echo` in the app container printed the sidecar's network IP and `curl` failed with "No route to host" (the runner got ECONNREFUSED on the same IP); without the entry the name resolved to a LAN address on the measuring host.
- **Canned answers** (the same sidecar): `POST /__e2e/answers { prefix, status, contentType, body }` makes requests whose path starts with `prefix` (any method, query string ignored) get that answer instead of `{}`; they are still recorded. One entry per prefix (the latest wins), the longest matching prefix answers, 10000 entries at most (the oldest dropped); an invalid entry (prefix not starting with `/`, status outside 100-599, a non-string body or content type, a body over 65536 bytes) is 400 and changes nothing. An entry may carry `barrier: { prefix, count, timeoutMs }` (prefix starting with `/`, integer count 2 to 100, integer timeoutMs 1 to 30000, else 400): the answer is withheld until `count` requests answered by entries with that barrier prefix are waiting at once, then all are answered together; if the group does not fill within `timeoutMs` of its first waiting request, they all get 504 `barrier timeout`. So receiving the canned answers proves the requests were waiting at the echo together. `EchoTarget.answer(subPath, { status, body, contentType, barrier: { subPath, count, timeoutMs } })` of the `echo` fixture sets one below the test's own target (the barrier's `subPath` is below the target too); it uses Node's `fetch` (a canned answer may hold a token). `src/lifecycle/mock-idp.ts` builds a mock Generic OAuth provider on it (token and user-info endpoints on the test's target); the server calls them itself, the browser never visits the provider, so a test signs in with the client's own call `POST /api/auth/tp/login` and a made-up code.
- **Mail sink** (the same sidecar, SMTP on port 2525; the app gets `LOWCODER_ADMIN_SMTP_HOST=e2e-echo`, port 2525, no login, no STARTTLS): accepts every
  mail the SERVER sends (password reset, invitation) and delivers it nowhere. One record `{ from, to[], data }` per message (`data` is the message as
  latin1 text, dot-stuffing undone; the 65536-byte cut counts the bytes as sent, before dot-stuffing is undone; 10000 records kept); `GET /__e2e/mails?to=<address>` answers those sent to an address
  (case-insensitive). Parsing is stream-safe (a command or the end of data may arrive in any number of TCP chunks); only EHLO, HELO, MAIL, RCPT,
  DATA, RSET, NOOP and QUIT are understood, anything else is 502. The `mailbox` fixture (`mailsTo`, `waitForMail`) reads it with Node's `fetch`, never a
  Playwright request context: a context created during a test lands in the trace, and the mails hold reset tokens (measured: a trace of a
  `newContext` read held the mail body, a trace of the `fetch` read held none). `src/lifecycle/mail.ts` parses a mail (nested multipart, 7bit, 8bit,
  binary, quoted-printable, base64, charsets, encoded-word subjects) and takes the token out of a reset link (`resetTokenOf`), or returns the reset link
  (`resetLinkOf`) or the invitation link (`inviteLinkOf`) exactly as mailed, to open as a page. Limits: no STARTTLS, no AUTH, and mails live for the whole run, so a test uses an address of its own. The links of the
  mails carry the configured public URL without its trailing slashes (D-54), so they read `http://lowcoder-e2e-app:3000/user/auth/lost-password?token=...`
  whatever run of slashes the run script's configured URL ends in.
- **Fixed app host name `lowcoder-e2e-app`** (`scripts/app-host.sh`): network alias of the app container;
  `LOWCODER_BASE_URL` is `http://lowcoder-e2e-app:3000`. Reason: the client's hocuspocus URL
  (`REACT_APP_HOCUSPOCUS_URL=ws://lowcoder-e2e-app:3000/hocuspocus`) is baked in at client build time and the guard
  compares every WebSocket host with the host of `LOWCODER_BASE_URL`. The name exists only inside a run's network; with
  `E2E_HOST_PORT` the chat components do not connect in a host browser.
- **Network guard** (`src/fixtures.ts`): HTTP(S) requests of a context to another origin are aborted with
  `blockedbyclient`; WebSockets to another host are closed with `socket.close()`. Service workers are blocked. The guard
  is installed only by the custom `test` exported from `src/fixtures.ts` (automatic fixture `networkGuard`, and
  `newUserSession` for further contexts). A spec that imports `test` from `@playwright/test` bypasses it; always import
  `test` and `expect` from `src/fixtures` (stack-free unit specs that open no page are the accepted exception, `AGENTS.md` section 8). `blocked-requests.txt` is attached only for the primary `networkGuard`;
  URLs blocked in a `newUserSession` context are not attached. The guard covers browser contexts, not requests made by
  the backend inside the app container (which needs internet only for `@npm`: node-service fetches npm packages).
- **Users and isolation:** most tests use the `apiUser` fixture (own user and organisation, registered through the
  API). Exceptions: stack-free unit tests register no user (the `actor` fixture of the security helpers registers its own users), `smoke/signup.spec.ts` registers through the UI, and
  `auth/login.spec.ts` calls `registerUser` directly. Writes to `notes` are scoped by an `owner` value; `products` is
  shared and read-only.
- **Config** (`playwright.config.ts`): `testDir ./tests`, 4 workers, test timeout 60 s, expect timeout 15 s, viewport
  1600x1000, `fullyParallel`. One global retry exists and only under `CI` (`retries: IS_CI ? 1 : 0`); S1 and M3 switch it
  off with `test.describe.configure({ retries: 0, ... })`. Reporters: list, html, junit and the D-3 threshold reporter.
  `LOWCODER_BASE_URL` is required.

## Quick start

All commands run from the repository root unless a directory is stated. Paths after `run-in-docker.sh` are relative to
`e2e/` (it is bound at `/work`), so write `tests/smoke/signup.spec.ts`, not `e2e/tests/...`.

Prerequisites for running: Docker (network, pulls of the app, PostgreSQL and Playwright images), `flock` (macOS:
`brew install flock`), network access to the npm registry from the runner.

Prerequisites for building the image (`e2e/scripts/build-e2e-image.sh`, several minutes): git with the ref `3.0.0`
present locally (`CLIENT_REF`), `tar`, `patch`, Docker, network access for image pulls, `apt-get` and `yarn --immutable`
inside the build container.

```bash
# repository root, once: build the image under test
e2e/scripts/build-e2e-image.sh

# repository root: default selection on a fresh stack (removed afterwards)
e2e/scripts/run-in-docker.sh

ls e2e/playwright-report e2e/test-results
```

Checks without a stack, from `e2e/`:

```bash
cd e2e
npm ci
./node_modules/.bin/tsc --noEmit        # success = exit status 0 and no TypeScript diagnostics
LOWCODER_BASE_URL=http://localhost:1 ./node_modules/.bin/playwright test --list --reporter=list
```

Always add `--reporter=list` to `--list`: the configured html and junit reporters write into `playwright-report` and
`test-results` and fail in a read-only workspace.

Gates (a gate run must not pass `--reporter=...`, see below):

```bash
# General repeat gate for a new or changed test or file (repository root)

# S1, the insert-every-component test (112 tests): ONCE, not --repeat-each; nightly command (repository root)

# M3, the module host built in the editor (repository root)

E2E_STACK_PROFILE=enterprise e2e/scripts/run-in-docker.sh --repeat-each=10 --workers=4 tests/security/enterprise.spec.ts
```

`--workers` only works as a CLI argument: `run-in-docker.sh` does not forward `E2E_WORKERS` into the runner.
A CLI `--reporter=...` REPLACES the reporters of `playwright.config.ts`, including the D-3 threshold reporter, so a
real S1 or M3 gate must not use it; a passing run prints `D-3 gate within the limit: ...` on stderr, and a missing line
means the gate did not run. `--reporter=list` is for `--list` only.

Quarantine decision rule: a test that asserts the DESIRED behaviour and fails today is `@quarantine`. A
characterisation or workaround test that passes while documenting a defect (CD-5, CD-7, CD-3 limits, D-3 handling) is not.

Annotation types used: `defect` (description = defect id) for a test that asserts or works around a defect;
`D-3 retry` and `handler retry` for the retries of S1/M3 and the editor-module tests; `observation` for a recorded
observation (`modules/module-versions.spec.ts`, O-12). Observations O-11 to O-15 are listed in the table above.

D-3 retry and threshold rules (code: `src/components/insert-all.ts`, `src/modules/moduleScenario.ts`,
`src/reporters/d3-threshold-reporter.ts`):

- S1 and M3 wait up to `SAVE_POLL_TIMEOUT_MS` (20 s) for the saved DSL to hold the edit. On a timeout the test adds the
  annotation `D-3 retry` and redoes its editor steps on a fresh app once; a second lost save fails the test.
- M3 has a second retry, `handler retry`, for its event-handler step. At most one of each per test.
- Both files set `test.describe.configure({ retries: 0, timeout: 180_000 })`, switching off the one CI retry.
- The reporter counts, per gated file, the tests that RAN and fails the run when more than `floor(ran / 2)` carry
  `D-3 retry`. The limits 56 of 112 (S1) and 5 of 10 (M3) apply to the complete gates above. A targeted run of fewer
  tests gets a proportionally smaller limit; a one-test run allows zero D-3 retries. A file that did not run is not judged.
- Limit: a regression that loses fewer than half of the first saves passes.

## Troubleshooting

- `another run uses .../e2e (lock .../e2e/.run.lock)`: a second `run-in-docker.sh` in the same checkout. Wait or use
  another checkout.
- `test-results` is empty or gone after a run: a concurrent run in the same checkout cleaned it (Playwright recreates
  `outputDir` at the start of a run). Never run two stacks, or a direct `playwright test`, in one checkout at once.
- Chat tests cannot connect (`ws://localhost:3006` in blocked requests): the image predates the baked
  `REACT_APP_HOCUSPOCUS_URL`; rebuild with `e2e/scripts/build-e2e-image.sh`.
- `image ... does not exist; build it with e2e/scripts/build-e2e-image.sh`: the default image is only a local tag.
- `@npm` tests time out or components render an empty area: the app container cannot reach the npm registry (CD-4 shows
  no error). `--grep-invert @npm` skips those tests, but the run still needs the npm registry for `npm ci`.
- `@playwright/test ... does not match the runner image`: align `package-lock.json` and `PLAYWRIGHT_IMAGE`; the script
  header has the lockfile command.
- A component dropped right after the editor opens is thin or zero-width: D-5; use `EditorPage.open()`.
- The app does not answer within 300 s: the script prints the last 60 log lines of the container.
